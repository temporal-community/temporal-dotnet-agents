# WorkingSet

Demonstrates `WorkingSetContextProvider` (Feature D) — a library-provided `AIContextProvider` that tracks recently-referenced file paths across turns and injects a compact working-set context note before each LLM call.

## Overview

A multi-turn code assistant reads mock C# source files across four turns. `WorkingSetContextProvider` accumulates the referenced file paths in the session's `AgentSessionStateBag` and injects a `## Working set` system note before each LLM step:

```
## Working set
Recently referenced files/paths in this session:
- src/Auth/AuthService.cs
- src/Data/UserRepository.cs
```

Paths must contain a separator — the extractor deliberately rejects bare filenames like
`AuthService.cs` to avoid matching ordinary prose. The sample's prompts therefore name real
repository-relative paths, which is how a developer addresses a coding agent anyway.

The sample also registers a small `WorkingSetEchoProvider` that prints the stored working set on
each LLM step, so you can see the set accumulate rather than having to infer it from the model's
wording:

```
[WorkingSet] src/Auth/AuthService.cs
[WorkingSet] src/Auth/AuthService.cs,src/Data/UserRepository.cs
```

By Turn 4 the working set is in the injected note, so the agent can answer "what files are we
working with?" without calling `list_files` again.

## What it demonstrates

- `WorkingSetContextProvider` — automatic working-set tracking from chat history
- Cross-turn context accumulation surviving in `AgentSessionStateBag`
- Turn 4: the injected context carries the working set, so the agent need not call `list_files` again
- How `AIContextProvider` fires once per LLM step and accumulates state through the session

## Prerequisites

- .NET 10 SDK
- Temporal Service 1.31.0 or newer on `localhost:7233` (local: `temporal server start-dev --namespace default --search-attribute AgentName=Keyword --search-attribute SessionCreatedAt=Datetime --search-attribute TurnCount=Int`)
- OpenAI API key configured via user-secrets:
  ```bash
  dotnet user-secrets set "OPENAI_API_KEY" "sk-..." --project samples/MAF/WorkingSet
  ```

## Configure credentials

```bash
dotnet user-secrets set "OPENAI_API_KEY" "sk-..." --project samples/MAF/WorkingSet
```

Optional — override the Temporal server address:
```bash
dotnet user-secrets set "TEMPORAL_ADDRESS" "your-server:7233" --project samples/MAF/WorkingSet
```

## Run

```bash
dotnet run --project samples/MAF/WorkingSet/WorkingSet.csproj
```

## Expected output

```
Worker started. Running four-turn code assistant session...

User : Show me the AuthService implementation
Agent: Here is the AuthService implementation: [describes AuthService.cs]

User : What does UserRepository look like?
Agent: UserRepository implements IUserRepository and provides GetUserByIdAsync and FindByEmailAsync methods...

User : How does auth relate to the repository?
Agent: AuthService depends on IUserRepository to validate tokens. It calls GetUserByIdAsync to look up the user by ID extracted from the JWT...

User : What files are we working with in this session?
Agent: Based on our conversation, we've been working with: AuthService.cs and UserRepository.cs

Done.
```

The exact agent wording varies because it is generated by the LLM. Turn 4's response is notable: the agent answers from the `## Working set` context note injected by `WorkingSetContextProvider` — no `list_files` tool call is needed.
